# 오디오 받아쓰기를 비동기 작업으로 바꾸는 설계

**작성일**: 2026-10-08
**상태**: 구현 완료 (2026-10-08)
**관련**: `2026-08-25-sermon-audio-fallback-design.md`의 받아쓰기 **호출 방식**(동기 `generateContent`, 함수 1회 안에서 완료)을 교체한다. 트리거 조건·모델 체인·결과 검사·종결 상태는 그 문서가 유효하다. 같은 변경에 업로드 감지 폴링 시간표(`2026-09-17-sermon-detection-polling-design.md`)와 자막 대기 횟수도 함께 고친다.

## 배경

2026-10-04 주일예배(64분, `sLZ52maHI0Q`)의 요약이 자막 확보 뒤 19시간 동안 생성되지 않았다. QStash 전달 기록(UTC)으로 확인한 경과:

| 시각          | 일                                                                                              |
| ------------- | ----------------------------------------------------------------------------------------------- |
| 07:11         | `fetch-audio-transcript` 발행. 300초에서 응답 없음(`status=-1`), QStash 재전달도 300초에서 종료 |
| 08:00·09:00   | `retry-summaries`가 진행 표시 만료를 보고 재발행. 두 번 다 같은 식으로 2회씩 종료               |
| 10:00 → 10:04 | 네 번째 발행에서 266초 만에 성공, `summarize` 발행                                              |
| 10:04:37      | `summarize`가 0.8초 만에 200 — 선점 거절(`not claimable`)                                       |
| 다음 날 05:30 | 관리자 "요약 재생성"으로 생성                                                                   |

결함이 두 겹이다.

1. **받아쓰기 시간이 함수 상한에 걸쳐 있다.** 7회 전달 중 6회가 Vercel `maxDuration` 300초에서 끊겼다. 주일예배는 최근 4주 중 3주(09-13·09-20·10-04) 자막 없이 이 경로를 탔다.
2. **오디오 회수와 요약 선점이 시도 횟수를 나눠 쓴다.** `reclaimStaleAudioTranscripts`가 회수마다 `summary_attempts`를 1 올리는데, `claimSermonById`와 `selectRetryTargets`는 같은 값이 `MAX_SUMMARY_ATTEMPTS` 미만이어야 움직인다. 세 번 회수한 뒤 받아쓰기가 성공하면 요약은 선점도 재시도도 되지 않고, 로그도 남지 않는다.

입력 구성도 문제였다. YouTube URL을 그대로 넘기면 받아쓰기에 쓰지 않는 영상 프레임이 함께 들어간다. 같은 영상의 `countTokens` 실측:

| 입력                     | VIDEO   | AUDIO   | 합계    |
| ------------------------ | ------- | ------- | ------- |
| URL만                    | 274,486 | 123,709 | 398,200 |
| `videoMetadata.fps` 0.02 | 5,538   | 123,709 | 129,252 |

20만 토큰을 넘으면 Pro preview는 입력 단가가 두 배다. fps 0.02로 Pro에 64분 전체를 동기 호출하면 147초 만에 끝까지(3861/3866초) 받아썼고, 저장본과 분량·고유명사가 같았다.

## 확정된 의사결정

| 항목             | 결정                                                                                                                                                                                                                                                                                           |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 호출 방식        | **Interactions API `background: true`**. 시작 job은 작업을 만들고 id만 넘긴다. 조회 job이 결과를 가져온다. Vercel 함수 상한과 받아쓰기 시간이 분리된다                                                                                                                                         |
| 입력             | `{ type: 'video', uri, processing: { type: 'static', fps: AUDIO_TRANSCRIPT_FPS } }`, fps **0.1**(10초에 1장). 프레임을 거의 빼면 타임스탬프가 밀린다 — 아래 "프레임 간격과 타임스탬프". background 요청에서 fps·구간 지정이 받아들여지는 것을 3.8 Flash·3.1 Pro preview 모두 실측으로 확인했다 |
| 모델 체인        | 기존 4단 그대로. 작업 **생성** 단계에서 일시 오류·404면 다음 모델로 넘긴다. 완료 후 실패는 모델을 바꾸지 않고 기존 재시도(`retryAudioTranscriptOrGiveUp`)로 넘긴다                                                                                                                             |
| 조회 간격·상한   | 30초 간격, 40회(20분). 상한을 넘으면 실패로 처리한다                                                                                                                                                                                                                                           |
| 진행 표시        | 시작 job이 남기고, 조회 job이 매번 만료 시각을 `AUDIO_TRANSCRIPT_STALE_MS`만큼 늘린다. 조회 사슬이 끊겨 만료되면 스위퍼가 기존대로 시작 job부터 다시 돌린다                                                                                                                                    |
| QStash 재전달    | 시작 job **0회** — 재전달되면 작업이 두 번 만들어진다. 조회 job **1회** — 조회는 멱등이고, 완료된 결과는 자막 유무 검사가 두 번째 처리를 막는다                                                                                                                                                |
| 결과 검사        | `model_output` 단계의 텍스트를 이어 붙여 기존 파서·`assertCoversFullAudio`에 넣는다. Interactions 응답에는 `finishReason`이 없어 중간 절단은 길이 검사가 잡는다                                                                                                                                |
| 시도 횟수        | 자막이 저장되는 순간(오디오 진행 표시를 푸는 UPDATE, 스위퍼의 인계 UPDATE) `summary_attempts`를 0으로 되돌린다. 오디오 단계의 횟수는 무한 회수를 막는 용도이고, 요약은 새 예산으로 시작한다                                                                                                    |
| 선점 거절 가시화 | `summarize`가 선점에 실패했을 때 행이 `none`/`failed`인데 횟수가 상한이면 `warning` 로그를 남긴다. 중복 전달로 인한 정상 거절(`pending`·`ready`)은 남기지 않는다                                                                                                                               |
| 동기 경로        | `manualSummarize`(로컬 스크립트)는 같은 시작·조회 함수를 프로세스 안에서 반복 호출해 기다린다. 요청 형식과 파싱은 한 곳에만 둔다                                                                                                                                                               |
| 소요 시간 로그   | 요약 완료·실패에 초와 모델, 오디오 시작·완료·실패에 모델과 초를 `app_logs`에 남긴다. 오디오 완료 초는 시작 job 시각부터 조회 job이 완료를 본 시각까지라 조회 간격만큼 길게 잡힌다                                                                                                              |
| 자막 대기        | `MAX_TRANSCRIPT_RETRY` 6 → **2**(1시간). 07-01 이후 등록돼 자막(오디오 아님)으로 요약된 25건 중 22건이 등록 후 62분 안에 자막을 확보했다(0·30·60분대). 나머지 3건(413·1221·1503분)은 3시간 대기 밖이었다                                                                                       |
| 업로드 감지 폴링 | 일 12:20부터 16:00까지, 수 20:20부터 21:20까지 KST **20분 간격**, 매일 09:00 유지. 근거는 아래 "폴링 시간표"                                                                                                                                                                                   |

## 흐름

```
fetch-transcript 2회 소진 / 스위퍼 회수 / 관리자 재생성
        │
        ▼
fetch-audio-transcript (시작 job, retries 0)
   a. 자막이 이미 있으면 종료
   b. markAudioTranscriptInFlight — pending + 만료 시각
   c. 모델 체인 순서로 background 작업 생성 (생성 단계 503·404면 다음 모델)
      실패 → 오디오 변환 실패 로그 + retryAudioTranscriptOrGiveUp
   d. "오디오 변환 시작" 로그
   e. poll-audio-transcript 발행 (30초 뒤, polls=0)
        │
        ▼
poll-audio-transcript (조회 job, retries 1)
   a. 자막이 이미 있으면 종료
   b. 작업 조회
      ├─ 진행 중·조회 오류 → polls < 40: 진행 표시 연장 + 30초 뒤 재발행
      │                       polls ≥ 40: 실패 처리
      ├─ 완료 → 파싱·길이 검사
      │         통과: publishSummarizeOrMarkFailed (자막 저장 + 표시 해제 + 시도 0 + summarize 발행)
      │               "오디오 변환 완료" 로그
      │         탈락: 실패 처리
      └─ failed·cancelled → 실패 처리
   실패 처리 = "오디오 변환 실패" 로그 + retryAudioTranscriptOrGiveUp
```

조회 job 본문은 `{ sermonId, videoId, attempt, interactionId, model, startedAt, polls }`다. 상태는 DB가 아니라 메시지에 실려 다니므로 스키마 변경이 없다.

## 프레임 간격과 타임스탬프

영상 프레임은 시각 기준점 구실도 한다. 2026-10-08, 10-04 영상을 3.1 Pro preview background로 받아쓰게 하고, 기준 문장이 찍힌 시각을 운영 저장본(전체 프레임 동기 호출, 497구간, "야라시" 37:13, "곰팡이" 45:45)과 비교했다.

| fps   | 줄 길이 지시 | 처리  | 입력 토큰 | 구간 | "야라시" | "곰팡이" |
| ----- | ------------ | ----- | --------- | ---- | -------- | -------- |
| 0.001 | 없음         | 304초 | 96,978    | 320  | +5:24    | +1:58    |
| 0.02  | 없음         | 282초 | 101,862   | 50   | −1:56    | −3:24    |
| 0.02  | 있음         | 285초 | 101,909   | 390  | −0:12    | −0:04    |
| 0.1   | 없음         | 187초 | 122,322   | 499  | +0:01    | −0:04    |
| 0.1   | 있음         | 306초 | 122,369   | 416  | +0:05    | 0:00     |

fps 0.001은 뒤로 갈수록 시각이 밀렸고, fps 0.02는 한 판에서 구간이 50개로 뭉쳐 챕터 시각이 몇 분씩 앞당겨졌다. fps 0.1이 저장본과 가장 가까웠다. 줄 길이 지시("한 줄에 한두 문장, 20초 이내")는 뭉침을 막았지만 fps 0.1에서는 이득이 없었다.

같은 날 fps 0.001 판 하나는 232초 뒤 `failed`로 끝났고 오류 메시지가 비어 있었다. 같은 조건을 다시 돌리면 완료됐다. 이런 실패는 기존 자동 재시도 1회가 받는다.

## 폴링 시간표

07-01 이후 YouTube 게시 시각(Data API `publishedAt`, KST):

| 유형 (요일)       | 건수 | 범위          | 비고                   |
| ----------------- | ---- | ------------- | ---------------------- |
| 주일예배 (일)     | 13   | 12:40 ~ 14:56 | 11건이 12:40 ~ 13:27   |
| 시온찬양대 (일)   | 11   | 12:23 ~ 14:28 |                        |
| 주일찬양예배 (일) | 3    | 15:14 ~ 15:37 | 같은 날 특송 1건 15:05 |
| 수요예배 (수)     | 11   | 20:29 ~ 20:54 |                        |

창 밖 지각 업로드가 5건 있었다(수 19:49·19:52, 금 19:01·20:33, 일 10:31). 매일 09시 실행이 다음 날 줍는다.

09-17에 정한 예배 시간대 스케줄 두 개는 운영 QStash에 등록된 적이 없다. 10-08 조회에서 `ycc-` 스케줄은 매일 09시 `reconcile-sermons`를 포함해 4개뿐이었고, 09-20 설교는 다음 날 09시에 감지됐다. 09-27부터는 WebSub 푸시가 돌아와 1분 안에 감지되고 있다. 푸시는 언제든 다시 끊길 수 있어 폴링을 주경로로 둔 09-17 결정은 그대로다.

cron은 UTC라 한 창을 여러 스케줄로 나눈다.

| scheduleId                       | cron             | KST               |
| -------------------------------- | ---------------- | ----------------- |
| `ycc-reconcile-sermons-sun-head` | `20,40 3 * * 0`  | 일 12:20, 12:40   |
| `ycc-reconcile-sermons-sun`      | `*/20 4-6 * * 0` | 일 13:00 ~ 15:40  |
| `ycc-reconcile-sermons-sun-tail` | `0 7 * * 0`      | 일 16:00          |
| `ycc-reconcile-sermons-wed`      | `20,40 11 * * 3` | 수 20:20, 20:40   |
| `ycc-reconcile-sermons-wed-tail` | `0,20 12 * * 3`  | 수 21:00, 21:20   |
| `ycc-reconcile-sermons`          | `0 0 * * *`      | 매일 09:00 (기존) |

매일 실행을 합쳐 주당 23회다. Data API는 호출당 1 unit이라 쿼터와 무관하다. Data API가 막혀 yt-api로 폴백하는 상태가 이어지면 매 실행이 yt-api를 부르므로 월 100회 가까이가 yt-api 한도(월 300회)에서 나간다.

## 검토했지만 기각한 대안

- **영상 프레임을 사실상 빼기(fps 0.001)**: 토큰은 가장 적지만 타임스탬프가 몇 분씩 밀린다. 챕터를 눌러 이동한 위치가 틀어진다. 위 "프레임 간격과 타임스탬프".
- **프롬프트에 줄 길이 지시 추가**: fps 0.02의 구간 뭉침은 막았지만 fps 0.1에서는 정확도가 나아지지 않았다. 지시를 늘리면 다른 판에서 어떻게 흔들릴지 모르는 변수만 하나 더 생긴다.

- **동기 호출 유지 + fps만 낮춤**: 147초로 상한의 절반이지만 모델 지연이 흔들리면 다시 걸린다. 실측 이전 판에서 같은 영상이 266초와 300초 초과 사이를 오갔다.
- **영상을 구간으로 나눠 두 job으로 받아쓰기**: `videoMetadata` 구간 지정이 YouTube URL에서도 오디오까지 자르는 것을 실측으로 확인했다(30:00~31:00 지정 시 입력 1,567 토큰, 출력이 `[30:00]`부터 시작). 다만 구간 경계에서 문장이 갈리고, 3.1 Pro preview는 구간 결과의 타임스탬프를 `[00:00]`부터 다시 매겨 오프셋 보정이 필요했다. 비동기 처리로 시간 문제가 없어지면 얻는 것이 없다.
- **Batch API**: 50% 저렴하지만 목표 처리 시간이 24시간이다. 요약은 예배 당일에 보여야 한다.

## 운영 반영

- 배포 뒤 `npm run qstash:schedules -- --apply`를 운영 origin으로 실행해야 폴링 시간표가 적용된다. 운영 쓰기라 사용자가 실행한다.
- 배포 시점에 날아다니던 `fetch-audio-transcript` 메시지는 본문 형식이 같아 새 시작 job이 그대로 받는다.

## 테스트

- 단위: 응답에서 받아쓰기 텍스트를 꺼내는 함수, 작업 생성의 모델 폴백, 조회 결과 판정(진행·완료·실패·검사 탈락).
- 통합(PGlite): 조회 job 상태 전이(진행 표시 연장, 완료 시 자막 저장·시도 0·발행, 상한 초과·실패 시 재시도 인계), 10-04 재현(시도 3에서 자막 저장 → 선점 성공), 스위퍼 인계 시 시도 0, 소요 시간이 담긴 로그 문구.
- 깨지는 기존 단언: 오디오 job 발행 옵션(`retries: 1`, `timeoutSeconds: 300`)이 `retries: 0`으로 바뀐다.
- 병합 전 실측: 10-04 영상으로 시작·조회 함수를 로컬에서 끝까지 한 번 돌린다.
